What does this mean?

What the table does (virtualizer settings)

Rows
The size of the data set. Only the rows on the screen exist as elements, so 100,000 rows cost about as much as 1,000.
Extra rendering (overscan)
Rows are prepared beyond the screen to reduce gaps during fast scrolling. This rich-content demo starts with 1000 px; the virtualizer's default remains 400 px.
Loading skeletons
Rows without data are rendered with loading. Keep their cells; their content can be empty. The row uses the estimated height and is excluded from height estimation.

What your app does (simulated here)

Server delay
How long the simulated server needs to deliver a page of 50 rows. Selecting 0 ms also completes pending requests immediately. Not a setting of the table.
Row elements: Pool
Rows stay associated with their logical index while they remain in the range. Outgoing rows are rebound to entering indices and moved with moveBefore() where supported, preserving their connected state. Surplus rows are parked for reuse. Browsers without that API start in Positional mode; Pool remains available for comparison but ordinary insertion may interrupt native momentum. Data changes still update retained rows.
Row elements: Keyed
Rows that stay are kept, new rows are created, leaving rows are deleted. This is what React, Angular or Vue do when you render the rows with key={position}.
Row elements: Positional
Element number n always shows the n-th rendered row. The initial reserve uses the measured row-height estimate rather than assuming every rich row is compact-sized. The requested range always takes precedence, and the pool retains its largest size. Near the end it starts earlier to keep all positions valid. Rows, cells and matching content nodes stay connected. Scrolling by one row rebinds every slot, so this can do more work than Pool.
Inspecting the DOM
Pool and Keyed keep rows whose logical indices stay in range; Positional rebinds each slot as the range shifts. Matching text and rich-content nodes are patched in place. The positional pool grows as needed and only shrinks with the data set or reset. Pool uses connected moves where supported, but surplus rows can still detach. The Created counter counts row elements, not text nodes.
App renders rows
When the app reacts to the range-change event. Immediately is best; later rendering shows the extra rendering area or skeleton pattern during fast scrolling.
Content arrives later
Some rows get an extra block half a second after they appear, like images. The table keeps the content you look at in place.

Status bar

FPS, p50
FPS counts frame callbacks over each 500 ms window, independently of the other statistics. p50 shows the median callback interval. Both include idle time, not table renders. At 120 Hz a callback interval is about 8.3 ms, at 60 Hz about 16.7 ms.
Visible / requested / rendered
What is on screen, what the table asked for, and what the app has rendered. If rendered lags behind requested, the app is slower than the scrolling.
Measured / estimate
Rows with a known height, and the guessed height of all other rows.
Drift, anchor fixes, reconciles
How the table keeps your place when heights change: corrections are collected (drift) and applied when scrolling stops (reconciles), so a running scroll is never interrupted.
Created / reused / pool
How many row elements the app has created, reused, and parked.
