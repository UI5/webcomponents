The problem

Every row costs work

A table row is not one thing. It is a row element, cells, texts, tags, buttons – and each of them has its own small inner structure.

The browser has to create, style, layout and paint every single one of them.

For example: 60 elements per row.
100,000 rows: 6 million elements.

At 120 Hz, one frame has 8.33 ms. Rendering all rows is the wrong place to spend it.

Solution 1 · less DOM

Render only what you can see

A screen shows maybe 10–20 rows. So we only create those – plus a few extra above and below.

While you scroll, rows that leave the screen are removed or reused for the rows that come in.

This is virtualization. Next question: which rows belong in the window?

Solution 2 · measured + estimated

Measure the window.
Estimate the rest.

Rows we have never rendered get an estimated height: the average of all rows we have measured so far. Before the first measurement, the app can give a hint (estimatedRowHeight).

ResizeObserver reports sizes after layout, including later changes. Each measured height replaces its guess.

Update the average when the sample has doubled and the change is meaningful. Loading placeholders do not enter the average.

Solution 3 · fast sums

Where does row 70,000 start? – in 17 steps

To place a row we need the sum of all heights above it. Adding them one by one means up to 100,000 additions – in every frame.

Instead, we keep a small tree of partial sums (a Fenwick tree). Each box knows the total height of a block of rows. Any sum needs only a few boxes:

  • Where does row i start? Add at most 17 boxes.
  • A row changed its height? Update at most 17 boxes.
  • Which row is at pixel y? Walk down the tree: 17 decisions.

17 because 217 = 131,072 ≥ 100,000.

Fast sums, including unseen rows

Two trees and one guess

Most rows are never measured. We don’t store a guess for each of them. Instead we keep two trees:

  • Tree 1: sum of the measured heights
  • Tree 2: how many rows are measured
start(i) = measuredSum(i) + (i − measuredCount(i)) × guess

When the guess changes, nothing has to be updated – it is just one number in the formula.

Solution 4 · preserve native scrolling

Let heights change.
Keep native momentum.

The obvious way to keep your place is to correct the scroll position. But on phones and trackpads, changing the scroll position can stop momentum scrolling.

Collect corrections as drift. Move the rendered rows as one block inside the shared grid, so columns stay aligned.

At native scrollend, reconcile drift with the scroll position. Move both together so the visible content stays in place.

Solution 5 · choose a stable anchor

Keep the row you are reading still

A row above you grows – maybe its data just arrived. Without care, everything below is pushed down and you lose your place.

Drift lets us correct positions without stopping momentum. We pick one row as the anchor and keep it exactly where it is. Which one?

  1. The row you jumped to
  2. The row with the keyboard focus
  3. The first row you can read (not a loading placeholder)

The same model · keyboard focus

Focus is a number, not an element

Hold Page Down: the next target row may not exist yet, or its element may be recycled.

Remember the logical row and column. Use the height model for page movement; keep focus in the table until the target row is rendered.

DOM recycling does not change the intended focus target.

Works with any framework

The table asks. Your app renders.

range-change { first: 120, last: 135 } → Your app · React, Angular, Vue, plain JS → rows 120–134 with position

The table never creates rows itself – frameworks want to own their elements. How your app reuses its row elements is up to you:

Keyed – like React key
Positional – rewrite all
Pool – park & reuse

Colors = element identity. Scrolling by 2 rows: keyed creates 2 and deletes 2, positional rewrites all, pool reuses 2.

For app developers

What you need to do: three things

1Listen

to the range-change event of ui5-table-virtualizer.

2Render

rows first to last−1, in order, each with its position.

3Flag

rows whose data is still loading with loading – keep the cells, empty is fine. The table draws the placeholder.

function Orders({ orders }) {
  const [range, setRange] = useState({ first: 0, last: 0 });
  const rows = Array.from({ length: range.last - range.first }, (_, offset) => {
    const i = range.first + offset, order = orders.get(i);
    return (
      <TableRow key={i} position={i} loading={!order}>
        <TableCell>{order?.id}</TableCell>
        <TableCell>{order?.text}</TableCell>
      </TableRow>
    );
  });
  return (
    <Table style={{ height: "400px" }}>
      <TableVirtualizer slot="features" rowCount={orders.size}
        onRangeChange={e => setRange(e.detail)} />
      <TableHeaderRow slot="headerRow">…</TableHeaderRow>
      {rows}
    </Table>
  );
}
// 1. listen
virtualizer.addEventListener("range-change", e => {
  const { first, last } = e.detail;

  // 2. render rows first..last-1 in order
  for (let i = first; i < last; i++) {
    const row = getRowElement(i);  // reuse from a pool
    row.position = i;
    const order = store.get(i);

    // 3. flag rows without data
    row.loading = !order;
    if (order) fillCells(row, order);
  }
  releaseRowsOutside(first, last);  // back to the pool
});

  • Keyboard and focus handling
  • Design loading placeholders
  • Keep track of which rows were measured
