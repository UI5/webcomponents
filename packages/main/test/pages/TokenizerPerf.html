Tokenizer — Performance Test Page

Use this page to measure tokenizer layout cost across branches.
Open DevTools → Performance → record while resizing the window or pressing the buttons below.

1. 1 200 items — 50 selected (resize stress test)

Resize the browser window. On main: every resize triggers O(N) DOM reads. On refactored: token widths are cached; resize costs one getBoundingClientRect().

2. 200 items — all selected ("N Items" button)

Tests the state where no single token fits and the component collapses to "N Items". Resize to see layout recalculation cost.

3. Mixed token widths — 30 selected

Tokens vary from 2 to 40 characters. Tests whether the layout engine correctly picks the break-point when token widths differ significantly.

4. Three MCBs simultaneously (combined layout pressure)

All three MCBs resize together. Tests whether multiple simultaneous tokenizers each pay the full O(N) layout cost (main) vs. O(1) cache hit (refactored).

5. Dynamic selection — add / remove tokens programmatically

Clicking the buttons below selects/deselects items in bulk. Tests how fast the tokenizer recalculates layout when the token set changes.

Select 100 Deselect all Select 50 long tokens Toggle all

6. Narrow container (300 px) — many tokens overflow

A small MCB with 20 tokens selected forces the nMore calculation to run many binary search iterations. Resize between narrow and wide to stress the layout switching.
